# SSHFS между клиентом и сервером

Проба экспортирует временную папку клиента по SFTP и монтирует ее на Linux-сервере. Клиент открывает SSH-соединение и связывает его со стандартными потоками локального `rclone serve sftp --stdio`. Сервер запускает `sshfs -o passive` и передает точку монтирования в контейнер как `/work`. Входящий порт на клиенте не требуется. Управляющие команды используют отдельные SSH-соединения

## Запуск

На клиенте нужны Python 3.9+, OpenSSH и rclone с поддержкой `serve sftp --stdio`. На выделенной Linux-машине нужны Docker, SSHFS 3, FUSE 3 и findmnt. Учетная запись для SSH должна иметь доступ к Docker. Для передачи mount непривилегированному UID сандбокса нужен параметр `user_allow_other` в `/etc/fuse.conf`. Родительский каталог точки монтирования доступен только пользователю пробы. Тест запускает контейнер с `--pull=never`, поэтому образ `python:3.12.10-alpine3.21` должен быть на сервере

В проверенной конфигурации sshd на тестовой ВМ использовал `ClientAliveInterval 2` и `ClientAliveCountMax 2`. Без серверного обнаружения потерянного клиента второй сценарий может закончиться по таймауту самой пробы. Из корня проекта, где `sshfs-lab` -- имя тестового сервера в ssh_config

```sh
python3 -m experiments.sshfs.probe sshfs-lab --repeats 3
```

Для отдельного файла настроек SSH есть аргумент `--config`. Результат сохраняется в `results/sshfs/<timestamp>.json`

## Что измеряется

Контейнер запускается с теми же параметрами изоляции, что и сандбокс харнеса. Проба проверяет тип ФС в `/proc/self/mountinfo`, UID 65534 и единственный интерфейс `lo`. Затем клиент создает файл, контейнер меняет его, клиент правит его повторно. Вторая сессия сначала читает данные предыдущей. Выбор пользовательской папки и управление монтированием через gateway в эту пробу не входят

При исправной связи `pread` на смещении 65536 возвращает 4096 байт. Второй дескриптор открыт для перезаписи существующего файла, первый блок из 4096 байт принят вызовом `write`, файл еще не закрыт. Клиент приостанавливает только SSH-процесс передачи данных через SIGSTOP. Контейнер повторяет чтение на том же смещении. Проба ждет 300 мс и проверяет, что ответ еще не пришел. В режиме `disconnect` клиент затем убивает транспорт через SIGKILL. В режиме `unresponsive` процесс остается остановленным и соединение закрывает сервер. Это воспроизводимая потеря ответов SSH при работающем TCP, других видов сетевых сбоев проба не моделирует

JSON содержит результат чтения, второго вызова write, закрытия дескриптора, создания нового файла после обрыва и запуска команды с рабочим каталогом `/work`. Состояние прерванной перезаписи на клиенте фиксируется до и после очистки. После каждого сценария проверяется отсутствие контейнера, временного серверного каталога и точки монтирования
