# HTTP v0

[Клиент и gateway](client.json) и [харнес и менеджер](sandbox.json) описаны в OpenAPI 3.1. Сейчас это синхронный срез. В нем есть один ответ на запрос, CLI получает трассу по окончании запуска. Поток событий, восстановление по курсору, отдельные ReadFile, WriteFile и collect входят в следующий этап

Для exec ненулевой exit_code означает завершение команды с ошибкой. timeout закрывает сессию, output_limit делает то же при превышении 64 КиБ. sandbox означает сбой Docker или отсутствие сандбокса. Сбой соединения клиент классифицирует как transport. После неоднозначного сетевого сбоя provision и exec автоматически не повторяются, поскольку первый запрос мог успеть выполниться. Для повторной очистки можно отправить release уже завершенной сессии

Клиент получает список простых задач авторизованным POST /v0/tasks с пустым JSON-объектом. Для каждого ID он вызывает POST /v0/smoke с task_id. Успешный HTTP-запрос возвращает результат чекера, включая pass=false при несовпадении ответа, трассу и превью выходного файла

POST /v0/smoke теперь всегда обращается к настроенной модели через model-proxy и записывает API-диалог. Поля mode, response_models и recording показывают происхождение результата. Ошибка запуска задачи сохраняется как outcome с pass=false, без обязательных trace_id и events. Токены могут быть null, если провайдер не вернул статистику. При отсутствующей конфигурации API возвращается HTTP 503 до создания сандбокса

Клиент с папкой открывает `/v0/workspaces/open` с одноразовым идентификатором монтирования и режимом `ro` или `rw`. Менеджер выбирает серверный путь сам и проверяет SSHFS из созданного контейнера. Вызов `/v0/workspaces/message` использует тот же контейнер и историю разговора. Ответ содержит финальный текст и выполненные команды с кодами выхода. Другое сообщение во время работы получает `busy`, закрытая или просроченная сессия -- `session`. Если папка недоступна при проверке до или после агентного цикла, запрос завершается с `mount_lost`. После ошибки выполнения gateway освобождает контейнер

CLI выбирает `message_id` перед отправкой. После потери ответа клиент вызывает `/v0/workspaces/status` с `session` и тем же ID. При `not_received` клиент повторяет отправку с этим ID, при `running` ждет. Состояние `completed` содержит исходный ответ, `failed` -- ошибку. Gateway резервирует ID до запуска. Повтор с другим текстом получает 409, повтор завершенного сообщения -- сохраненный результат. Запрос без ID работает по прежнему синхронному протоколу. Статусы доступны до закрытия сессии, истечения 180 секунд с открытия или перезапуска gateway

Повторный `/v0/workspaces/close` безопасен. Закрытие удаляет контейнер и историю диалога из gateway. Идентификатор сессии не восстанавливает историю после перезапуска gateway. Файлы рабочей папки не собираются для чекера, вывод выбранных моделью команд передается провайдеру как контекст разговора

В режиме записи HTTP-ответ на сообщение завершает работу харнеса в рабочей копии. Вердикт о публикации дает клиент после сверки файлов на Mac. При конфликте CLI печатает исходный путь и путь к предложению агента, затем завершает сессию с ненулевым кодом
