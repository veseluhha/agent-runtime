## SSHFS между macOS и Debian, 4 ноября

Клиент -- macOS arm64, сервер -- отдельная ВМ Debian 12.15 под QEMU с Linux 6.1, SSHFS 3.7.3 и Docker 20.10.24. На клиенте каталог экспортировался через rclone 1.74.4. В шести сессиях сандбокс видел `fuse.sshfs` в `/work`. В каждой сессии он прочитал файл клиента, изменил его и увидел следующую правку с Mac. После создания новой сессии ранее закрытые файлы снова читались

| Обрыв во время чтения | Повторы | Что увидел процесс в сандбоксе |
| --- | --- | --- |
| Завершение SSH-процесса клиента | 3 | После SIGKILL чтение вернуло 0 байт за 4–7 мс |
| Приостановка SSH-процесса без закрытия TCP | 3 | Чтение оставалось заблокированным 12,021–12,027 с, затем вернуло 0 байт |

До обрыва чтение тех же 4096 байт по тому же смещению проходило успешно. Тайминги относятся к этой ВМ и настройкам sshd с ClientAliveInterval 2 и ClientAliveCountMax 2. В первом сценарии время отсчитывается от SIGKILL после 300 мс подтвержденного ожидания, во втором -- от начала заблокированного чтения

Во всех шести сессиях новый файл после обрыва создать не удалось (ENOTCONN). Контейнер оставался запущенным, но новый docker exec с рабочим каталогом `/work` завершался с кодом 126 на этапе chdir. Уже закрытая запись сохранилась на Mac. У другого файла агент успел записать первый блок, затем получил ошибку при попытке записать второй и закрыть дескриптор. После очистки во всех шести случаях на клиенте остались первые 4096 байт вместо исходного файла. После остановки клиента без закрытия TCP до очистки еще читалась старая версия этого файла

После каждой сессии проба проверила удаление контейнера, серверного каталога и точки монтирования. Время восстановления действующего сандбокса и поведение при потере пакетов в физической сети не измерялись
