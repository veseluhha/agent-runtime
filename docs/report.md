## SSHFS между macOS и Debian, 4 ноября

Клиент -- macOS arm64, сервер -- отдельная ВМ Debian 12.15 под QEMU с Linux 6.1, SSHFS 3.7.3 и Docker 20.10.24. На клиенте каталог экспортировался через rclone 1.74.4. В шести сессиях сандбокс видел `fuse.sshfs` в `/work`. В каждой сессии он прочитал файл клиента, изменил его и увидел следующую правку с Mac. После создания новой сессии ранее закрытые файлы снова читались

| Обрыв во время чтения | Повторы | Что увидел процесс в сандбоксе |
| --- | --- | --- |
| Завершение SSH-процесса клиента | 3 | После SIGKILL чтение вернуло 0 байт за 4–7 мс |
| Приостановка SSH-процесса без закрытия TCP | 3 | Чтение оставалось заблокированным 12,021–12,027 с, затем вернуло 0 байт |

До обрыва чтение тех же 4096 байт по тому же смещению проходило успешно. Тайминги относятся к этой ВМ и настройкам sshd с ClientAliveInterval 2 и ClientAliveCountMax 2. В первом сценарии время отсчитывается от SIGKILL после 300 мс подтвержденного ожидания, во втором -- от начала заблокированного чтения

Во всех шести сессиях новый файл после обрыва создать не удалось (ENOTCONN). Контейнер оставался запущенным, но новый docker exec с рабочим каталогом `/work` завершался с кодом 126 на этапе chdir. Уже закрытая запись сохранилась на Mac. У другого файла агент успел записать первый блок, затем получил ошибку при попытке записать второй и закрыть дескриптор. После очистки во всех шести случаях на клиенте остались первые 4096 байт вместо исходного файла. После остановки клиента без закрытия TCP до очистки еще читалась старая версия этого файла

После каждой сессии проба проверила удаление контейнера, серверного каталога и точки монтирования. Время восстановления действующего сандбокса и поведение при потере пакетов в физической сети не измерялись

## Клиентская папка на macOS, 19 ноября

На Debian с Docker 20.10 и SSHFS 3 подняты gateway, менеджер и прокси. DeepSeek через OpenRouter изменил только строку установки в README на Mac. Между сообщениями клиент положил в папку случайную строку, модель прочитала ее из файла в том же контейнере. В режиме чтения обычная запись из контейнера завершилась ошибкой. После отключения SSHFS следующий запрос вернул `mount_lost`, каталог монтирования и контейнер обеих сессий были удалены

В первом запуске CLI изменение на диске состоялось, второе сообщение завершилось ошибкой протокола модели. После сохранения полей финального ответа провайдера сквозная проверка с двумя сообщениями прошла. Точная причина первого ответа не установлена. Один успешный прогон не дает оценки частоты сбоев. В отдельном запуске при пересоздании gateway во время сообщения оборвалось управляющее соединение

## Дозапись, обрыв и конфликт редакторов

На первом варианте CLI (rclone VFS `off`) команда `printf '+agent' >> candidate` вернула 0, но на Mac осталась только исходная строка. Rclone сообщил об ошибке записи по смещению. После включения `writes`, синхронной публикации при закрытии и `sshfs_sync` оба прогона сохранили полную строку `original+agent`. Во втором прогоне агент также заново прочитал тот же README после внешней правки на Mac

В каждой из двух проб процесс держал открытыми целевой файл и временную копию, записал по 4096 байт и остановился до следующего блока. После потери транспорта продолжение записи не удалось, в исходном файле сохранились 8 байт `original`, временная копия на Mac отсутствовала. Результат относится к обрыву до закрытия дескриптора в этой конфигурации

В отдельном контроле агент подготовил новую версию на основе `original`, клиент изменил целевой файл на `client edit`, затем агент выполнил `os.replace`. В обоих прогонах на Mac осталась `original+agent`. Замена целого файла не сохранила параллельную правку клиента
